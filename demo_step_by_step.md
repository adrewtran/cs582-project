# CRM Sales Opportunities: Step-by-Step Demo

> The demo of the evidence-grounded agent (one command: `python -m src.agent_demo`) and the professor presentation guide are in `docs/EXCELLENT_PROJECT_DEMO_STEP_BY_STEP.md`. This file covers the prediction pipeline and the simulated-data scenario.

Total time is about 15–20 minutes. The demo has two scenarios that run the same models on different data:

| | Scenario A: original data | Scenario B: simulated data |
|---|---|---|
| Data | `data/crm/`: Maven Analytics CRM, a public fictitious dataset (8,800 deals) | `data/crm_simulated/`: 100,000 deals generated by the team from a known formula |
| Purpose | The project's main, reported result | A check that the pipeline finds signal when signal exists |
| Run | `src.run_project` | `scripts/simulation/run_simulated_models.py` |
| Results | `reports/crm/final/` | `data/crm_simulated/model_results.csv` |
| Test ROC-AUC | about 0.50–0.52 (no better than chance) | about 0.87 (best possible is 0.88) |

Results from full runs of both scenarios are already saved, so the demo can use them and skip the long training runs.

## Step 0: Set the story
- **Goal:** predict whether a CRM sales opportunity will be Won or Lost, and explain which factors drive the score.
- **Input:** four CRM tables (pipeline, accounts, products, teams).
- **Output:** a Won/Lost probability and the factors that influence it.
- **Honest framing:** on the original data the models are weak (test ROC-AUC about 0.50–0.52). Present this as a rigorous, leakage-free study, not a production model.
- **Why two scenarios:** the simulated data shows that the same pipeline and models do learn when the data contains signal. The low scores on the original data therefore come from the data, not from a broken pipeline. Simulated scores are never real-world performance.

## Step 1: Install (once, before the demo) — macOS
No GPU is needed. The tested environment is **Python 3.12 on Linux, CPU only**. macOS has **not** been tested by the team, so run this whole step once before the demo day and fix any problem early. Windows and Linux notes are at the end of this step.

**1a. Install the tools** (Terminal):
```bash
git --version                       # check that git is installed
brew install python@3.12            # needs Homebrew: https://brew.sh
python3.12 --version                # should print Python 3.12.x
```
If `python3.12` is not found after installing, close and reopen Terminal. On Apple Silicon the binary is at `/opt/homebrew/bin/python3.12`, on Intel Macs at `/usr/local/bin/python3.12`. Python 3.13 and 3.14 are rejected by the project, so do not use `python3` if it points to them.

**1b. Get the code:**
```bash
git clone https://github.com/thai-phan/cs582-project.git
cd cs582-project
git checkout main
```
`main` is the default branch.

**1c. Create the virtual environment:**
```bash
python3.12 -m venv .venv-crm
source .venv-crm/bin/activate       # optional; the prompt now starts with (.venv-crm)
which python                        # with the venv active, should end in .venv-crm/bin/python
```
Creating it by hand is optional: `scripts/tools/setup_cpu.py` creates `.venv-crm` itself if it is missing and reuses it if it exists. Keep the name `.venv-crm`, because every later command calls `.venv-crm/bin/python`. Run `deactivate` to leave the venv. The commands in this guide call the venv's Python directly, so activating it is not required.

**1d. Install the dependencies into the venv:**
```bash
python3.12 scripts/tools/setup_cpu.py     # installs CPU torch first, then requirements.txt, then runs pip check
```
The first install can take several minutes. To start over, delete the `.venv-crm` folder and run steps 1c and 1d again.

**1e. Check that the install worked:**
```bash
.venv-crm/bin/python -c "import sklearn, torch, pytorch_tabnet; print('ok')"
```
If `setup_cpu.py` stops with a version error, you are not using Python 3.12.

**Other systems:**
- **Ubuntu/Debian:** `sudo apt install python3.12 python3.12-venv` (older releases may need the deadsnakes PPA), then the same commands as above.
- **Windows:** install Python 3.12 from <https://www.python.org/downloads/> and tick "Add python.exe to PATH". The interpreter is `.venv-crm\Scripts\python.exe` and activation is `.venv-crm\Scripts\Activate.ps1`. Windows has not been tested.

# Scenario A: original data (Steps 3–7)

## Step 3: Show the full pipeline (pick one)
- **Live:** `.venv-crm/bin/python -m src.run_project`. This takes a few minutes because it trains Dummy, LR, RF, MLP, TabNet and CatBoost on two feature sets on CPU and then runs the agent experiment (about an hour in total). To show the stages separately: `python -m src.train`, then `python -m src.evaluate`, then `python -m src.predict`.
- **Faster:** skip the run and open the existing `reports/crm/final`.

## Step 4: Walk through the results in `reports/crm/final`
1. `run_manifest.json`: shows `status: complete` and `mode: full`.
2. `data/data_quality.json` and `checks/leakage_audit.csv`: `close_value`, `close_date`, `deal_stage` and `opportunity_id` are excluded from the predictors.
3. `data/split_manifest.csv`: the time-based split gives train 2,975, validation 583, test 1,361, with 1,792 rows purged because their outcomes weren't known at the cutoff.
4. `models/selection_lock.json`, `metrics/feature_set_comparison.csv` and `metrics/test_metrics.csv`: history-feature LR was chosen on validation ROC-AUC before the test was scored. The Dummy model has high accuracy and F1 because it always predicts Won.
5. `metrics/calibration_test.csv`: calibration improved Brier from 0.3180 to 0.2489, which is still worse than Dummy at 0.2421.
6. `figures/`: ROC curves and confusion matrices.

## Step 5: Show the explanations
- `explain/feature_importance_*.csv` and `explain/permutation_importance_test.csv`: which features move the score.
- `models/explanation_reference.json`: the training reference values behind the per-deal sensitivities of the selected model. These are not causes.
- `explain/rf_shap_global.csv` and `explain/shap_audit.json`: RF SHAP as a separate diagnostic, with additivity error under 1e-5.

## Step 6: Show scoring of open deals
Open `predictions/open_deal_predictions.csv` (or rerun `python -m src.predict`). It has 1,589 Engaging rows with `win_probability` and `loss_probability` summing to 1. Rows with a missing account are flagged. Priority is only a heuristic, and open deals are never labelled Lost.

## Step 7: Estimate 3-month expected revenue (illustrative)
```bash
python scripts/analysis/expected_revenue_3m.py
```
It multiplies each open deal's `win_probability` by the product's list `sales_price`, then simulates wins and losses 10,000 times. The output goes to `reports/crm/final/predictions/expected_revenue_3m.json`, labelled `ILLUSTRATIVE_NOT_A_VALIDATED_FORECAST`.
- **Result:** about 2.50M expected from 1,589 open deals (3.89M if all were won). The simulated range is about 2.38M–2.63M.
- **Account present only:** 501 deals, about 0.83M expected.
- **Why 3 months and not 2 years:** deals close within 138 days (median 45), so the current pipeline covers a short horizon. The data spans only about 10 months and comes from a fictitious practice dataset, so a 2-year forecast is not supported.
- **Say it carefully:** the model is weak (ROC-AUC about 0.5), the range ignores model error, prices are list prices rather than `close_value`, and new deals are not included.

# Scenario B: simulated data (Step 8)

## Step 8: Run the same models on simulated data (about 3 min)

**8a. Explain the data.** Open `SIMULATED_DATA.md`, sections 1 and 3.
- The simulated data reuses the real accounts, sales agents and products, and matches the real date range and a win rate of about 0.63.
- It adds 9 invented products, competitor products and 5-year industry trends.
- Each deal's win probability comes from a formula the team wrote. It includes three interaction effects, such as "expensive product **and** small account". The interaction strength is k = 3, the "strong" setting.
- `ground_truth.csv` stores each deal's true win probability. This is the answer key. It is never used as a feature.

**8b. Run it.**
```bash
.venv-crm/bin/python scripts/simulation/run_simulated_models.py --quick    # about 20 seconds
```
This trains the same models (the saved results cover Dummy, LR, RF, MLP and TabNet; the script now also fits CatBoost) with the same loader, time-based split, preprocessing, threshold rule and metrics as Scenario A. Each model is trained twice:
- **base:** the standard CRM features, as in Scenario A.
- **extended:** base plus sector match, industry trend and competitor comparison.

`--quick` uses tiny budgets and writes `model_results_quick.csv`, so the stored results are not replaced. The full run (no `--quick`) takes about 5–6 minutes and overwrites `data/crm_simulated/model_results.csv`.

**8c. Walk through the stored results** in `data/crm_simulated/model_results.csv` (rows with `split = test`).
- **Split:** train 32,470, validation 4,920, test 14,322, with 19,751 rows purged by the same rule as Scenario A.

| Test ROC-AUC | base features | extended features |
|---|---|---|
| Dummy | 0.500 | 0.500 |
| Logistic Regression | 0.784 | 0.809 |
| Random Forest | 0.840 | 0.864 |
| MLP | 0.838 | 0.866 |
| TabNet | 0.840 | 0.867 |
| **Oracle** (true win probability, the best possible) | 0.878 | 0.878 |

- With extended features, RF, MLP and TabNet come within about 0.01 of the oracle. They recover nearly all of the planted signal.
- Logistic Regression trails by about 0.055, because it cannot represent the interaction effects.

**8d. Show that the result is stable.** Open `data/crm_simulated/seed_summary.csv` and look at the rows with `interaction_strength = 3.0`. These come from 5 newly generated datasets. With extended features, test ROC-AUC is LR 0.827 ± 0.008, RF 0.872 ± 0.007, MLP 0.873 ± 0.008 and TabNet 0.875 ± 0.008, against an oracle of 0.886 ± 0.007.

**8e. Compare the two scenarios.**

| | Scenario A: original | Scenario B: simulated |
|---|---|---|
| Best test ROC-AUC | about 0.52 | 0.867 (oracle 0.878) |
| Best model vs Dummy | no real gain | large gain |
| What it shows | The available features carry almost no signal about Won/Lost | The pipeline and models do learn real structure when it exists |

- **Say it carefully:** the simulated formula was written by the team, so a high score there proves only that the models can learn that formula. It is not evidence about real sales. Nonlinear models win partly because the data was built with interactions. Simulated results are never mixed into `reports/crm/final/`.

## Step 11: Close with the limitations
**Original data (Scenario A):**
- The data covers closed deals only, so there is selection bias.
- The validation set was reused.
- The account, team and product tables are static snapshots.
- Accounts repeat across periods.
- The dataset was examined in earlier attempts, so the test set isn't pristine.
- Results don't yet prove the model helps sales prioritisation.

**Simulated data (Scenario B):**
- The win/loss rule is invented, so the scores measure recovery of a planted pattern, not real-world accuracy.
- Each seed generates a new dataset, but the model seed stays at 42, so variation from model initialisation is not measured.

## Tips
- Have `reports/crm/final` and `data/crm_simulated/model_results.csv` pre-opened in case a live run is slow.
- Always say which scenario a number comes from. Never quote a simulated score as the project's result.
- TabNet results can vary slightly across platforms, so don't promise exact decimals.
